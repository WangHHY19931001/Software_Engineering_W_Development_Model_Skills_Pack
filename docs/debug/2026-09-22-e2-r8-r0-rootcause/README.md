## 1. 缺陷陈述

W-Model 技能包约束「阶段 1 的闭环五门必须在放行记录之前成功」（`check-run-log.ts` R11，
`w-model-dev/scripts/logic/run-log-logic.ts:1434-1487`）与「`check-checkpoint.ts` 的 R0 零证据
守卫要求 run-log 已存在 checkpoint 放行记录」（`w-model-dev/scripts/logic/checkpoint-logic.ts:222-227`）
构成**首阶段自举死锁**。D-6（`c05b4f09`，2026-09-21）以「阶段 1 后置窗口」豁免了 R11 侧，但
真实时序（写放行记录 → 跑 check-checkpoint → 记录其成功）在 R8 侧仍产生三条违规——
run-log 门在阶段 1 自举场景仍 exit 1。历史调测的实际绕法是「放行后复跑 + 时间戳重对齐」
（`docs/debug/2026-09-20-wm-8phase-live-run/README.md:62,71`），属伪造证据时序的簿记操作。

**本次实测复现（HEAD `6dd683f4`，fixture 为合成最小 run-log）**：

- **D-6 时序**（放行记录在前、check-checkpoint 的 gate 记录在后）→ `check-run-log.ts` **exit 1**，
  恰好三条 R8 违规：
  1. `R8: 阶段 1 checkpoint 非阶段最后记录（checkpoint 之后仍有 1 条动作…）`
  2. `R8: 阶段 1 gate 动作(gate)出现在 checkpoint 之后，理想轨迹中 gate 先于 checkpoint`
  3. `R8: 阶段 1 轨迹顺序倒置：G(gate 类)(第 8 条) 晚于 checkpoint(第 7 条)…`
- **自然时序**（用户确认 → 五门全在放行前 → 放行记录为阶段末条）→ `check-run-log.ts` **exit 0**
  （R8/R11 全绿，仅 1 条非阻断 diagnostic）。**即：自然时序被现行的 R8/R11 判据完全接纳，
  唯一过不去的是 R0——check-checkpoint 在该时序下自身 exit 1**（§8 复现 1：
  违规恰为一条 `run-log 无 checkpoint success 记录…`）。

这一复现把缺陷的落点收窄为一句话：**R8/R11 的时序契约本身没有问题，问题在 R0 把首阶段
放行的证据锚点钉死在派生记录上，强制生产者采用「先写记录后跑门」的 D-6 时序，而该时序
又被 R8 判非法。**

## 3. 5-Why 缺陷链

**Why 1：为什么阶段 1 自举场景 run-log 门必红？**
D-6 只放宽了 R11 的时间轴（`run-log-logic.ts:1468-1474`），未动 R8。唯一可行时序「写放行
记录 → 跑 check-checkpoint → 追加其成功 gate 记录」使 gate 记录落在放行记录之后，同时命中
R8-1（`:1212-1217`）、R8-2（`:1219-1227`）、legacy 链序倒置（`:1359-1377`）三条（§1 实测）；
反向时序（先跑门）则 check-checkpoint 因 R0（`checkpoint-logic.ts:222-227`）自身 exit 1，
R11 拿不到 `gateExitCode=0` 记录（`:1465` 过滤），同样红。两条时序全红 ⇒ 必红。

**Why 2：为什么 R8 与 R11 无法同时满足？**
R11 把 `check-checkpoint.ts` 列入「放行前闭环」五脚本（`:58-64`），即要求**验证放行的门先于
放行成功**；而 R0 又要求该门运行时 run-log 里**已有放行记录**。「被校验事件的记录必须先写、
校验该记录的门的后置记录必须后写、后写的记录又必须不存在（R8：checkpoint 为阶段终点）」——
三条判据各自局部合理，联合起来对「零放行记录态」（阶段 1）无解。

**Why 3：为什么 check-checkpoint 会以「放行记录已存在」为前提？**
R0（`c5edcfc8`，2026-09-18 审计修复）把「放行发生过」的证据**唯一锚定**在 run-log 的
checkpoint success 记录（派生证据）上。而系统里存在**更强且写入更早的初级证据**：用户确认
原文（checkpoint-log/phase-N 文件，R3 以它防代签，`checkpoint-logic.ts:267-287`）。R0 完全
没有消费这路证据。又因 R0 的过滤器是全局的（`:220`），阶段 ≥2 的历史放行记录使
`checkpoints.length > 0` 恒真，冲突被掩盖——只有阶段 1（零记录态）正面暴露。

**Why 4：为什么 R0 当时锚定派生证据？**
R0 的立法目的只是关闭 fail-open 审计漏洞（提交 `c5edcfc8`：「close fail-open gates…」；修复
前空 run-log 在 check-checkpoint 上**静默判通过**）。审计修复取了最小实现「记录为空即违规」，
未区分「零证据」与「证据在别处」。当时闭环时序契约 R11（`d98e2a03`）次日才合入，两规则的
时间轴耦合尚未显形，规格层没有机会审视「首阶段证据源」问题（J1 收口规格
`docs/superpowers/specs/2026-09-18-leftovers-closeout-design.md:46` 只转述 hard-constraints #11
文本，全篇无「自举/bootstrap」字样——已核实）。

**Why 5（根因层）：为什么冲突以「必红」形态存在而三批规则各自合入时都绿灯？**
因为**放行记录在规则体系中被赋予了两个不可同时满足的角色**，而没有任何一条规则声明这一
分工：R0/R11 把它当**放行事件凭证**（必须先写、供门校验、R11 以其时间戳为放行时刻），
R8 把它当**阶段终点轨迹标记**（必须最后写、其后不得有任何记录）。规则演化分四批独立落地
（R8 `82ba421d` 2026-08-10 → R0 `c5edcfc8` 2026-09-18 → R11 `d98e2a03` 2026-09-19 →
D-6 `c05b4f09` 2026-09-21），每批只对自己契约负责；D-6 规格只授权 R11 侧豁免（§5），R8 侧
冲突虽被 E-2 登记却按「不擅自扩范围」搁置——于是「必红」被原样保留到今天。

## 4. 根因结论（工作假设裁定）

**控制器工作假设：成立，并作一处精化。**

> 假设原文：根因 = checkpoint 放行记录的角色混淆 + R0 的证据源错配——同一条放行记录同时
> 承担「放行事件凭证」（R0）与「阶段终点轨迹标记」（R8）两个角色；而放行的初级证据其实是
> checkpoint-log 的用户确认文件，R0 却锚定在 run-log 记录这一派生证据上。对阶段 ≥2，历史
> 放行记录的存在掩盖了冲突；对阶段 1，两个角色在同一条记录上正面相撞。

逐点裁定：

- **角色混淆**：✅ 成立（Why 2 / Why 5）。且实测证明 R8 的轨迹判据本身能接纳自然时序——
  角色冲突不是 R8「过严」，而是 R0 强迫生产者走 D-6 时序才撞上 R8。
- **证据源错配**：✅ 成立（Why 3）。R3 早已把 checkpoint-log 定位为用户确认的权威源
  （拒绝代签），R0 却对它零消费；「阶段 ≥2 历史记录掩盖冲突」亦由 `:220` 全局过滤器核实。
- **精化 1（R11 是放大器而非根源）**：即使 R0 改锚，R11 仍宣称「验证放行的门先于放行」——
  对一个**以放行记录存在为运行前提**的门，这一契约在任何阶段都只能靠「门空转/凭历史记录
  通过」来满足（阶段 ≥2 今天正是如此：`checkpoints` 全局过滤使 phase N 的 pre-release 运行
  实际校验的是 phase 1..N-1 的记录，当前阶段记录的内容校验后置到 phase N+1 回溯完成）。
  因此完整根因表述为：**规则层从未定义 check-checkpoint 在首阶段的自举语义——它被同时
  当作「放行前闭环门」（R11）与「放行记录的验证者（以记录存在为前提）」（R0）使用，而其
  真正在首阶段可校验的初级证据（用户确认在场）未被任何规则引用。**
- **精化 2（后果链有实证）**：角色混淆 + 证据错配不只是「红」，它**教唆伪造**——历史调测为
  让 D-6 时序过 R8，采用了时间戳重对齐与记录移除（`README.md:62,71`；2 次移除误录记录与
  R7 append-only 精神相悖，`run-log-logic.ts:1100-1111` 只能验时间单调、无法验「记录未被
  删除」）。根因修复应同时消除「必红」与「伪造动机」。

### 5.2 D-6 为什么只修了 R11 侧——规格漏了还是有意收缩？

**有意收缩，且当时知道收缩的代价。** 证据链：

2. 但 ledger E-2（`progress.md:92-98`）写于同一晚且明确指出「R11 变绿后 R8 仍报三条……
   规格 §6 只授权了 R11 侧豁免」，处置为**不擅自扩范围**（分支纪律：超出已批准规格的实施
   会被 G/R3 拒绝）——即决策者当时已完整知道 D-6 是半解，选择登记挂起而非扩权实施。
3. `operational-recovery.md:484` 的「已知张力」节如实登记了后果（含「不得据此回退、改写
   记录或伪造时间戳」）——文档层无隐瞒。
4. 更早一层（Why 4）：J1/R11 引入时（`2026-09-18-leftovers-closeout-design.md:46`）没有做
   首阶段时序可行性分析——若当时做了，死锁会在 R0+R11 合入的同周被发现，而非等真实调测
   撞上。**这一层是规格遗漏；D-6 层是有意收缩。**

### 5.3 历史绕法为何是反模式级

「放行后复跑 + 时间戳重对齐」要让 R8 也绿，唯一手法是把后置 gate 记录的时间戳改到放行之前
（或删记录重排）——直接制造虚假时序证据，且与 R7 append-only 审计语义冲突。它每次都「能
跑通」，意味着技能包在真实项目上**系统性激励**伪证：这是比「红」更严重的失效形态（红至少
诚实）。

### B：R0 首阶段形态（零放行记录时以 checkpoint-log 为初级证据）——**推荐**

语义：`checkpoints.length === 0` 时，若 `options.checkpointLog` 在场且含非空 phase-1 用户确认
→ R0 不违规（首阶段自举形态：以初级证据证明「放行将被用户授权」）；否则照旧违规。
（零放行记录 ⇒ 下一次放行必然是首放行 ⇒ 无需 `--phase` 入参即可精确定界，与 CLI 现状
（无 `--phase`，§2 补充核实）天然契合。）

| 兼容性     | ◎ 变化方向单一：唯一从红变绿的形态 = 「run-log 零放行记录 + checkpoint-log 含 phase-1 确认」。`samples/checkpoint/` 两个 fixture（`valid.jsonl`/`bad-empty-decisions.jsonl`，均含 checkpoint 记录）不走该形态；run-log 侧样本/负向案例零波及（run-log-logic 未动）；既有 demo 历史 run-log 判定不变。需同步 load-bearing 登记（`checkpoint-logic-rule-loadbearing.test.ts:60-62` 锚与禁语保留，新增分支用例）。诚实边界：首放行记录的 R1/R2/R4 内容校验后置到下一阶段 check-checkpoint 的全局回溯——这与现行阶段 ≥2 的既有语义**完全一致**（今天 phase N 的记录同样由 phase N+1 回溯校验，`checkpoints` 全局过滤 `:220`），非本方案新引入的缺口；可加一条非阻断 diagnostic 提示（可选加固，不阻塞） |
