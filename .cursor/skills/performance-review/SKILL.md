# 性能评审：负载压测 + 指标达标判定

对代码或服务执行性能评审：按负载模型（ramp-up → sustain → ramp-down）运行 k6 / JMeter 负载脚本，从响应时间、吞吐、资源占用、负载模型四个维度采集数据，将结果与生产目标值（targetValue）/ 测试环境基线（testThreshold）比对，只有全部指标达标且高负载无崩溃才给出"性能达标"结论。质量标准的权威定义见 `w-model-dev/references/quality-standards.md`（性能指标监控行与禁止行为 #5）。

<HARD-GATE>
在完成下方检查清单的全部条目（指标基线确认 → 负载模型压测 → 响应时间/吞吐/资源占用核验 → 达标判定 → 不达标时定位修复重测）之前，不得向用户宣称"性能达标"或"性能通过"。任何性能结论都必须是可复现负载压测的结果，禁止仅凭 happy path 或单次请求判定通过。
</HARD-GATE>

## 性能评审维度

评审至少覆盖以下四个维度，任一维度不达标均不得给出"性能达标"结论：

| 维度 | 通过阈值 | 采集方式 |
|---|---|---|
| 响应时间 | P95 响应 < 2s | 负载脚本输出百分位分布（k6 的 `http_req_duration` / JMeter 聚合报告） |
| 吞吐 | QPS/TPS 与并发数随负载曲线变化 | 负载脚本统计每秒请求数 / 事务数 |
| 资源占用 | CPU / 内存 / IO 无异常飙升，无持续泄漏与峰值溢出 | 压测期间采集宿主指标（top / 监控面板），压测后确认资源回落 |
| 负载模型 | 按 ramp-up → sustain → ramp-down 三段式完整压测 | 负载脚本按阶段配置并发与时长，覆盖峰值窗口 |

**响应时间**：以 P95 响应 < 2s 为硬性通过阈值（对齐 `quality-standards.md` 性能指标监控行）。只看平均值会被少数慢请求掩盖，必须检查百分位分布。

**吞吐**：关注 QPS（每秒查询数）/ TPS（每秒事务数）随并发变化的曲线，确认系统在目标并发下吞吐不塌陷、无明显拐点。

**资源占用**：压测全程记录 CPU / 内存 / IO。重点排查内存随请求数线性增长（泄漏）、CPU 长时间满载、IO 排队堆积。压测结束后资源应回落到压测前水平。

**负载模型**：必须按 ramp-up（逐步加压）→ sustain（稳定保持峰值负载）→ ramp-down（逐步减压）三段式压测，覆盖系统从空载到峰值再回落的完整过程。仅跑 happy path（单请求 / 低并发冒烟）不得作为性能判定依据（禁止行为 #5）。

## 生产目标值 vs 测试环境基线

性能指标必须区分生产目标值与测试环境基线（对齐 `quality-standards.md`"生产目标值 vs 测试环境基线"节，区分原则见该文件）：

1. **生产目标值（targetValue）**：生产环境须达成的硬性指标。例如 P95 响应 < 2s、高负载无崩溃，是最终放行依据。
2. **测试环境基线（testThreshold）**：测试环境的放宽阈值。引用时必须声明三项：
   - **测试环境类型**（如本地开发机 / CI 容器 / 预发环境）
   - **放宽倍数**（如 ×2 响应时间、×0.5 并发）
   - **放宽原因**（如硬件规格低于生产、共享 CI 资源波动、无真实数据量）

**反模式**：将测试环境阈值直接套用于生产；未声明测试环境类型、放宽倍数与放宽原因。测试环境达标不构成生产达标的证据——报告生产结论时必须回到 targetValue 口径核对。

## 工具与压测

**负载工具**：使用 k6 或 JMeter 编写负载脚本（对齐 `quality-standards.md` 性能指标监控行），按负载模型配置 ramp-up → sustain → ramp-down 三个阶段：

```bash
# k6 示例：三段式负载脚本（阶段时长与并发按被测服务实际调整）
k6 run -e TARGET_URL=http://localhost:8080 load-test.js
```

```js
// load-test.js：ramp-up → sustain → ramp-down
export const options = {
  stages: [
    { duration: "2m", target: 200 },  // ramp-up：逐步加压到 200 并发
    { duration: "5m", target: 200 },  // sustain：保持峰值负载
    { duration: "2m", target: 0 },    // ramp-down：逐步减压至 0
  ],
};
```

JMeter 等价做法：用线程组 + 阶梯加压插件（或手动多线程组）实现同样的三段式负载曲线，并在聚合报告中读取 P95 响应与吞吐。

**判定规则**：

- **P95 响应 < 2s 且高负载无崩溃** → 性能指标达标（对齐 `quality-standards.md` 质量门检查清单"性能指标达标（P95 响应 < 2s，高负载无崩溃）"）
- **P95 不达标或高负载崩溃** → 回到编码定位瓶颈（数据库慢查询、无缓存、串行化、资源争抢等），修复后按同一负载模型重测，直到达标
- **禁止仅跑 happy path 判定性能通过**（禁止行为 #5）：单次请求成功、低并发冒烟通过都不构成性能达标的证据，必须按负载模型完成三段式压测

## 检查清单

你必须为以下每个条目创建任务，并按顺序完成：

1. **指标基线确认** — 明确被测服务与端点，确认生产目标值（targetValue：P95 响应 < 2s、高负载无崩溃）与测试环境基线（testThreshold：测试环境类型、放宽倍数、放宽原因），二者不得混用
2. **负载模型压测** — 编写并运行 k6 / JMeter 负载脚本，按 ramp-up → sustain → ramp-down 三段式完整压测，禁止仅跑 happy path
3. **响应时间核验** — 从压测结果读取 P95 响应，确认 < 2s；不达标则记录具体数值与对应瓶颈现象
4. **吞吐核验** — 确认 QPS/TPS 与并发曲线：目标并发下吞吐不塌陷、无明显拐点
5. **资源占用核验** — 核验 CPU / 内存 / IO：无异常峰值、压测后资源回落、无持续泄漏
6. **达标判定** — 以上各项均通过（P95 < 2s、高负载无崩溃）才给出"性能达标"结论；任一不达标不得放行
7. **不达标时定位修复重测** — 回到编码定位瓶颈，修复后按同一负载模型重测，直到全部指标达标再给出结论

## 与 security-review 的对称说明

安全与性能同属质量门（`quality-standards.md` 质量门检查清单）的非功能维度：security-review 负责安全漏洞扫描与凭据脱敏，performance-review 负责负载压测与指标达标判定。二者共享同一门禁逻辑——结论必须来自可复现检查的结果：安全结论以 `npm run lint:security` 复扫为准，性能结论以负载模型压测数据为准；在完成全部检查清单条目之前，security-review 不得宣称"安全通过"，本技能不得宣称"性能达标"。
